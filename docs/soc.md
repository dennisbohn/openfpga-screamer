# CPU system

Contract between the hardware (`core/src/fpga/core/soc.v`) and the firmware (`firmware/`).
Whoever changes one side changes the other and this document. Memory system details (SDRAM
controller, caches, clock phase): `docs/memory.md`. Overall architecture:
`docs/architecture.md`.

## Overview

- **CPU:** VexRiscv `VexPocketIMFC` (RV32IM + F + CfuPlugin, 8 KB I-cache, 8 KB write-through
  D-cache, no MMU), generated by `tools/vexriscv/gen.sh`.
- **Clock:** everything runs on `clk_74a` (74.25 MHz) with no clock crossing to the bridge,
  the SDRAM controller included. Only `dram_clk` comes from its own PLL with adjustable
  phase (`docs/memory.md`).
- **Reset:** the CPU is held in reset while `reset_n` from `core_bridge_cmd` is low. The
  Pocket loads the data slots without `deferload` before "Reset Exit", so the firmware is
  already in the boot RAM at start. Reloading the firmware from the Pocket menu resets the
  core (parameter bit 6) without loading a new bitstream. After every reset buffer 0 is
  front, no swap is pending and `SYS_SIM` is 0. Until the first swap `video_out` shows buffer 0
  with palette 0: black after the core was loaded, or whatever the previous run left there
  after a firmware reload.
- **Firmware:** two parts. Data slot 0 `firmware.bin` (at most 32 KB) goes to bridge address
  `0x00000000`, the boot RAM: the loader (self-tests, quick memory test). Data slot 2
  `program.bin` (at most 1 MB, `core/data.json`) goes to `0x1300_0000` in the SDRAM: the
  program.
- **SDRAM slots only after the phase search:** slot 2 (`program.bin`) and slots 3 to 8 (the
  game files) are `deferload`; the Pocket does not load them by itself. The memory test's
  phase search runs the SDRAM at bad phases too, where the chip can misread commands and
  addresses and write anywhere (measured: 15 of 63 MB changed). The loader therefore
  requests `program.bin` only after the SDRAM tests (`DS_*`, `core_bridge_cmd` target
  command 0x0180): first the 16 header bytes that hold the size, then the file. The program
  fetches the game files the same way (`firmware/slot.c`). Their sizes come from the slot
  table the Pocket writes through the bridge for every slot, `deferload` ones included
  (bridge address `0xF800_2000`, per slot its id and size); `DS_SIZE` reads it, since the
  table of contents of a container is at its end. The bridge delivers 32-bit words big-endian
  (first file byte in bits 31:24), the CPU is little-endian: `soc.v` swaps the bytes on
  writes, so both sides see the ordinary little-endian image.
- **Program start:** `program.bin` begins with a header of four words: `"SCRP"`
  (`0x50524353`), size in bytes, CRC-32 of the bytes after the header, entry address. After
  the memory test the loader checks it (test "program", `SYS_SIM` bit 4), flushes the D-cache,
  executes `fence.i` and jumps with `a0` = its results (`SYS_SIM` bits), `a1`, `a2` = position
  and begun word in the log. The program sets its own `gp`, `tp` and `mtvec`; its stack is at
  the top of the boot RAM (from `0x8000` downwards to `0x6000`; the loader stays below).
  Nothing is shown meanwhile except a swap with a black palette, so that a reset does not
  leave the previous run's picture; the first frame is the program's loading screen. If a
  self-test or a memory test fails, or `program.bin` is missing, the loader starts nothing
  and the results stay on the screen.

## CPU memory map

| Address | Size | Content | Cached |
|---|---|---|---|
| `0x0000_0000` | 32 KB | Boot RAM: the loader, above it the program's stack. Reset vector `0x0000_0000`, `mtvec` after reset `0x0000_0020` | yes |
| `0x1000_0000` | 64 MB | SDRAM, see the layout below | yes |
| `0xF000_0000` | 4 KB | System and memory registers | no |
| `0xF000_1000` | 4 KB | Video registers and palette | no |
| `0xF000_2000` | 4 KB | Input | no |
| `0xF000_3000` | 4 KB | Rasterizer, setup and geometry units, blitter | no |
| `0xF000_4000` | 4 KB | Sound: the mixer | no |
| `0xF000_8000` | 4 KB | Log (`debug.txt`, see below) | no |
| `0xF100_0000` | 64,000 B | Framebuffer 0 | no |
| `0xF101_0000` | 64,000 B | Framebuffer 1 | no |
| `0xF400_0000` | 64 MB | SDRAM, the same memory uncached | no |

|---|---|

| `0x1210_0000` | track image (built by the firmware) |
| `0x1280_0000` | game files: `MAPnH.DAT` `0x1280_0000` (slots 3, 9-13), `GAME.DAT` `0x12C0_0000` (4), `MAPn.DAT` `0x12D0_0000` (5, 14-18), `GEN.DAT` `0x12D4_0000` (6), `LOCAL.DAT` `0x12D5_0000` (7) |

`0xF000_0000`-`0xFFFF_FFFF` is uncached for the CPU (`StaticMemoryTranslatorPlugin`). A
read outside the ranges gives a bus error (trap), a write there is ignored. Code runs only
from the boot RAM and from `0x1000_0000`; an instruction fetch from anywhere else, the
uncached SDRAM window included, is an access fault. SDRAM accesses are byte, halfword or
word; a read always returns the whole word and the CPU picks the bytes. Code written to the
SDRAM with stores needs `fence.i` and three more instructions afterwards (`icache_sync()` in
`firmware/hw.h`); data not written by the CPU (the bridge) needs a D-cache flush first
(`0x0000500F`, `dcache_invalidate()`).

## Registers

All registers are 32 bits wide, accessed as words.

## Sound

The mixer (`audio.v`) runs once per output value (48 kHz) through the 32 voices, one every four
clocks, with a shared datapath: the stored byte at the voice's position (the nearest sample,
nothing smoothed, like the game's driver), centred, times volume left and right, summed,
limited to 16 bits; then the position advances by the step, back into its loop or to the end.
The registers are in MLABs; for each voice the line (32 bytes) around its position is in an
M10K; when the position moves into another line, the pass fetches it over the line port
(ahead of the rasterizer), long before it is needed. Output is I2S to the Pocket at the
template's timing: MCLK 12.288 MHz from a fractional divider on `clk_74a`, bit clock
MCLK / 4, 64 bits per value, LRCK low left, high right, 16 bits each MSB first from the second
bit clock of the half. A CPU reset stops all voices; the output keeps running.

After the voices the same pass plays the music, eight clocks: a stream of 16-bit stereo at
44.1 kHz (the CD) from a 256 KB ring in the SDRAM that the firmware fills. For each side the
two values around the position, interpolated linearly between them (16-bit fraction,
rounded down), times volume (>> 15) into the sums; then the position advances by 60211 / 65536
values (44,100 / 48,000, 3 ppm too slow). The two lines around the position (16 values) are in
one MLAB; when the position moves into the second, the pass fetches the following one over the
line port, once per eight values. The voices' multiplier computes the four products (hence
18 x 18 bits wide); the sums have 22 bits. The firmware (`firmware/music.c`) fills the ring
from `SCREAM.gog` (slot 22): completely at the start of a song, afterwards once per frame
with a 32 KB read command that it only starts (`slot_start`); `AU_MUSIC` tells it how far the
mixer is. This costs the CPU about 500 clocks per frame (`docs/frame_timeline.svg`, "music");
the bridge writes 176 KB/s into the SDRAM. In the simulation the output is the CD track value
for value for 4.9 s (`tools/musiccheck.py`).

The firmware (`firmware/sound.c`) plays the effects from `SFXSBASE.DTR` (GEN.DAT): the samples
are unpacked in `SOUND.DAT`, the mixer reads them directly from the loaded container. Volume:
the list row times the master volume for effects, `0x4000` of `0x7fff`, two thirds of the
game's value (`0x6000`, `0x1bc2f`): the player's engine and the three opponent engines then stay
below 16 bits even with every sample at full scale (at most 32,000). A full sample moves the
output by 128 per 8-bit step.

Sounds with a location (OpenScreamer's notes, sections 15 and 17) are heard at the camera,
with the distance d in x and y; `car_step` sets it every step (`snd_ear`). Opponent engines
(`oppmotor`, `0x1dffc`, `opp.c`): only cars within 35000 units and only the three nearest,
volume ((35000 - d) / 35000)^2 * 23552, pitch speed * 2.4 + 13568; until green the speed is
sin(car number * 0.5 * clock) * 15000, so the opponents rev up (`0x20e63`; below the lowest
pitch the voice stays silent). The moving parts of the track (`0x21b80`, `scenery.c`): the
fourth column of `ANIMATIONS` names a row of the track's own `SOUND_FX` list in `MAPnDAT.DTR`
(track 1: `truck`, `airplane`), loaded after the effects and the commentator; within 40000
units, volume ((40000 - d) / 40000)^2, pitch 65536. Both get Doppler, + 9 per unit that the
source came closer in one game frame (1/30 s), here per step * 50 / 30; it is omitted when the
camera jumps over 1000 units in one step (a cut). Only these sounds are placed in the stereo
image: the line to the source in the camera frame, pan = 0x8000 +- 32767 *
sqrt(|lateral| / d), the far side linearly quieter; the player's own sounds stay centred.

The commentator (`firmware/speech.c`, OpenScreamer's notes section 17, "commentary"; EXE
`0x2479c`, `0x24820`, `0x24a24`, `0x2425c`): its recordings are the rows of `SPFXBASE.DTR` and
`SPFXFULL.DTR` (GEN.DAT, 11 + 47), loaded after the effects; the game's table (`0x1fb0`)
gives each of the 27 events up to three of them. An event enters a queue with mode (recording
0-2 or round robin) and delay, each at most once. While the voice is silent a clock runs; the
event with the shortest delay is served once the clock reaches it, and after the sentence the
clock restarts, so two sentences never overlap. Triggers: the countdown with the start lights
(`0x20d45`: 0, 2, 4, 6 s), checkpoint (recording after the remaining time), finish line (lap;
"new lap record" below the record, without `CHOICE.DAT` the game's 180 s), crash, the end
(won, lost, time up) and per step the guards of `0x2425c` with their times: wrong direction
(against the road at the last wall, `+0x13c`), standstill, hurry, lead and losing it, corner
(marker flag 4), sliding, last place, a lap ahead, contact with an opponent. The voice is
centred, with its own master volume `0x3000` (in the game effects, commentator and music all
start at `0x6000`; the recordings are normalised to full scale). With `0x4000` like the
effects the countdown clipped over the revving engines at the start and the music in the
simulation (7 values); with `0x3000` (the voice 2.5 dB below the game's ratio) the peak stays
at 28,631 of 32,767. Each sentence goes into the debug log when it ends: `say <from>-<to>
<event> <recording>` (race clock), as long as the 4 KB have room; after the report of the
start frame and the line every 250 frames it is full.

## Framebuffer

Each 320 x 200 bytes, one byte per pixel (palette index), row by row, pixel (x, y) at offset
`y*320 + x`. Byte, halfword and word accesses; reading works too. Byte order as in CPU
memory: the pixel with the smallest x is at the smallest address.

Sequence of a frame: wait until `VID_STATUS` bit 1 = 0. Back buffer = not bit 0. Write the
back buffer and its palette, then write `VID_SWAP`.

## Log to the SD card

Without JTAG this is the way to get errors and measurements off the Pocket: the firmware
writes text into the 4 KB area from `0xF000_8000` (byte, halfword and word accesses, reading
works too; little-endian as elsewhere, lines end with `\n`, the rest stays `\0`). The area is
the nonvolatile data slot `debug.txt` (id 1, bridge address `0x0010_0000`): when the core is
quit from the menu ("Quit") and at power-off the Pocket reads it through the bridge and
saves it as `/Saves/screamer/Chainy.Screamer/debug.txt` (the core does not support sleep,
`core.json`: `sleep_supported: false`). This works after a CPU crash too, because the
read-out is pure hardware. `soc.v` swaps the byte order so the file is readable text, and
after start enters the size 4096 for the slot in the core's slot table (which is otherwise
set only when an existing file is loaded).

On load the Pocket writes the old `debug.txt` (or `0xFF` if there is none) into the area;
`soc.v` ignores that. After loading the core the area therefore reads `0` until the firmware
writes; if the CPU does not start at all, the saved file consists of zeros instead of the old
log. A firmware reload from the menu is only a reset: until the new firmware clears the area,
the previous run's log is still there.

**Saved games** take the same path but live in the SDRAM: the nonvolatile data slots
`CHOICE.DAT` (id 23, `0x13F0_0000`, 1120 bytes: the original's settings file with options,
championship, records and unlocks) and `ATTACK.DAT` (id 24, `0x13F1_0000`, 6 x 60,016 bytes:
per track the kept time-trial run, `struct ghost_file` in `ghost.h`, which `ghost.c` reads
and writes directly there). Both are `deferload`: the firmware reads them right after start
(`save_load` in `save.c`); without a file, or for a `CHOICE.DAT` that does not look like the
original's, it takes the original's defaults (`0x1bbb8`) and then enters the full size into
the slot table with `DS_SIZE`, so the Pocket saves them on exit. From then on every CPU write
there (`choice` in `champ.h`) is already the saved game; the Pocket reads it on exit through
the bridge from the SDRAM (`sdram_port.v`: a bridge read word goes to the controller right
after the bridge's write buffer and has until the next bridge word, at least 88 clocks, to
complete). If the core is quit before `save_load` ran (in the first second), the Pocket saves
whatever is in the SDRAM there.

**Erasing the saves** from the Pocket menu (`core/interact.json`): the checkbox "Allow Save
Reset" writes a 1 through the bridge to `0x13FF_0000`, the action "Reset Save Data" writes one
to `0x13FF_0004`, both into the SDRAM (free between `ATTACK.DAT` and the last window of the
memory test; `save_load` clears both words at start). In every frame of every loop of the game
(menus, intro, race, pause, PLAY AGAIN?, fade-out) the firmware looks at them uncached
(`save_reset` in `save.c`, `next_frame` in `main.c`). Only with the checkbox set does it reset
both saves in the SDRAM to the defaults used for missing files, clear both words, stop effects
and music and jump back to the start of the game behind `save_load` (`setjmp`/`longjmp`):
first frame, loading, intro as at start. Without the checkbox it clears only the action
word. It does not re-read the files on the SD card: the old ones stay there until the core is
quit, then the Pocket writes the defaults back.

At start the firmware clears the area, writes a header line, the self-test results and
measurements; the trap handler adds cause and address of a crash (`mcause`, `mepc`, `mtval`).

## CPU quirks

- VexRiscv's `reset` is active high and asynchronous; `soc.v` releases it synchronously to
  `clk`.
- There is no `mscratch`; missing CSRs do not trap, `ebreak` traps as an illegal instruction.
- The instruction cache (`InstructionCache.scala`) clears its error flag `hadError` when a
  line has finished loading, but sets it again in the same clock if the last word of the line
  reports an error; then the next loaded line is also treated as faulty, and the trap handler
  runs into a second trap. `soc.v` therefore reports the error of a line outside the boot RAM
  with the first seven words only; the line is still marked faulty. The data cache does not
  have the problem.
- The FPU's fused multiply-add rounds the product before the addition (`FpuCore.scala`: "FMA
  Precision lost"). GCC turns `a*b+c` into `fmadd.s` by default; where results must be
  bit-identical to a PC build (OpenScreamer's physics), compile with `-ffp-contract=off`.
- The FPU's answer to a comparison (`flt.s`, `fle.s`, `feq.s`) or a conversion to integer
  (`fcvt.w.s`) returns late; an instruction that needs it right after waits. Several questions
  asked in a row return side by side and the CPU waits once: `firmware/track.c` (`INT_NOW...`)
  and `firmware/opp.c` (`ASKED...`) keep GCC from consuming each one separately with an empty
  `asm` that takes the answers as operands.
- GCC compiles `fminf`/`fmaxf` here with a call to `__issignalingf` before the `fmin.s`; in a
  loop this is slower than compare and branch.
- picolibc's `memset` and `memcpy` work byte by byte; `= { 0 }` of a large local array also
  becomes a `memset` call.

## Custom instruction (CFU)

`custom-0` (opcode `0x0B`), R format, `function_id = {funct7, funct3}`:

| funct7 | funct3 | Result |
|---|---|---|
| 0 | 0 | `(rs1 * rs2) >> 16`, signed (16.16 fixed point) |

```c
static inline int32_t fixmul(int32_t a, int32_t b)
{
    int32_t r;
    __asm__ volatile (".insn r 0x0B, 0, 0, %0, %1, %2" : "=r"(r) : "r"(a), "r"(b));
    return r;
}
```

## Simulation checks (`sim/soc`)

The testbench loads the slots like the Pocket (at most one bridge word per 88 clocks, waiting
for the acknowledge before the SDRAM slot), lets the CPU run and checks:

- `SYS_SIM`: once the firmware has drawn and swapped three frames it writes
  `0x80000000 | bits`. Bit 0 = integer, bit 1 = floating point (add, mul, div, sqrt,
  conversion), bit 2 = CFU; bits 3..12 = memory test (`firmware/memtest.c`): SDRAM ready, slot,
  phase, data bus, byte lanes, address bus, patterns, code, refresh, write status. Expected:
  `0x80001FFF`. On a trap it writes `0xC0000000 | mcause`.
- **Model:** the SDRAM model reports no error (command sequences, timings, bus conflicts);
  the longest gap between two AUTO REFRESH stays below 580 clocks.
- **Test strip:** the top 8 rows of every frame the firmware draws have the palette index x
  in columns x < 256, and the palette of every frame is
  `pal[i] = (i << 16) | ((255 - i) << 8) | ((i * 3) & 255)`. The testbench compares these
  pixels in the displayed frame.
- **Log:** the testbench reads it through the bridge like the Pocket (one word more, the first
  answer discarded), expects the header line, no "FAIL", the simulation's windows and in the
  first run "SDRAM slot: ok". Before the start it checks that `soc.v` ignores the loading of
  the log slot.
- **Resets** like a firmware reload from the menu (only `firmware.bin` reloaded): once while
  buffer 1 is front (in reset, swap request, front buffer and `SYS_SIM` must be 0), once in the
  middle of the memory test's SDRAM traffic. The last run must pass like the first, report
  the SDRAM slot as "skipped" and must not swap anything before the CPU's first request.

The SDRAM controller has its own random test (`sim/sdram`, see `docs/memory.md`). Negative
tests: `tools/sim_faults.sh` builds one fault into the SDRAM model per run; for any expected
value other than `0x80001FFF` (and without trap bits) the testbench requires exactly that
value, at least one "FAIL" in the log, and skips the resets.

Fault tests: `tools/fw.sh FAULT=IFETCH` builds a firmware that jumps to `0x0000_8000`, past
the boot RAM, after the self-tests (into `build/firmware-IFETCH/`, not onto the SD card).
Expected: `SYS_SIM = 0xC0000001` (access fault on instruction fetch), the trap handler's box
in the picture and the line `TRAP mcause=00000001` in the log. This also checks that the trap
handler runs out of the instruction cache after the error (see "CPU quirks"):

```sh
tools/fw.sh FAULT=IFETCH
tools/sim.sh soc build/firmware-IFETCH/firmware.bin build/sim/soc_ifetch 80 c0000001
```
