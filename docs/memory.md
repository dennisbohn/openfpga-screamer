# Memory system

SDRAM, caches, boot RAM and the memory test. The contract between CPU firmware and hardware
(addresses, registers, boot flow) is `docs/soc.md`; this document describes how the memory
side is built and why.

## Memories

- **Boot RAM** (32 KB, block RAM): the loader and, above it, the program's stack. Loaded by
  the Pocket through the bridge (data slot 0) before reset is released. Cached by the CPU.
- **SDRAM** (64 MB): main memory for program and data through the I-cache and D-cache,
  plus an uncached window (`0xF400_0000`) for tests and a write path from the APF bridge
  through which the Pocket loads data slots straight into it. Besides the CPU, the line port
  serves the rasterizer (textures), geometry unit (meshes), blitter (images) and mixer
  (samples).
- **Caches:** 8 KB I-cache and 8 KB write-through D-cache, 32-byte lines (8 words). Both
  fill lines through `sdram_port.v`.
- The Pocket's SRAM and PSRAM are not used; their pins are driven inactive in `core_top.v`.

The SDRAM chip is an AS4C32M16MSA-6BIN mobile SDRAM: 4 banks x 8192 rows x 1024 columns x
16 bit, 1.8 V, IO bank 7A, synchronous (`dram_clk`), no chip select.

SDRAM timing at 74.25 MHz (T = 13.468 ns), from the data sheet, in clocks:

| CL | tRCD | tRP | tRAS | tRC | tRRD | tWR | tRFC | tMRD | Refresh |
|---|---|---|---|---|---|---|---|---|---|
| 2 (allowed up to 83 MHz) | 2 | 2 | 4 | 5 | 1 | 2 | 11 (138 ns, safer than the 80 ns of the table) | 2 | 8192 per 64 ms: every 7.8 us = 580 clocks |

## Clock and IO timing

Everything runs on `clk_74a`, the SDRAM controller included: no clock crossing between CPU,
controller and bridge.

`dram_clk` comes from a second PLL, `pll_sdram` (reference `clk_74a`, output 74.25 MHz,
integer ratio, generated by `tools/gen_pll_sdram.sh` with Intel's `ip-generate`), through a DDIO
register (`altddio_out`, high = 1, low = 0). The requested phase is 10,000 ps; Quartus
chooses VCO 742.5 MHz (M = 10, C = 10) and delivers **9932 ps** (265.5 degrees). One step of
dynamic phase shift is an eighth of the VCO period, **168 ps**; 80 steps are one period. The
template PLL cannot produce 74.25 MHz next to 12.288 MHz, hence the second PLL.

Timing margin in the core itself (Quartus 18.1.1, phase 9932 ps, constraints as below, with
the 0.3 ns extra uncertainty), slack in ns, report of `tools/sta_sdram.tcl`:

| Corner | Output setup | Output hold | Read setup | Read hold |
|---|---|---|---|---|
| Slow 85 C | 3.134 | 2.656 | **0.841** | 4.415 |
| Slow 0 C | 3.235 | 2.678 | 1.432 | 3.990 |
| Fast 85 C | 4.802 | 2.862 | 5.658 | 1.563 |
| Fast 0 C | 4.920 | 2.795 | 6.230 | **1.060** |

The read window is tight at setup in the slow corner and at hold in the fast one. The
model does not know PLL jitter at the IO (up to 0.88 ns), the board or tOH at small load,
so the real window is found by measuring on the Pocket:

- **Phase adjustable at run time:** the SDRAM PLL has its dynamic phase shift ports
  (`phase_en`, `updn`, `cntsel`, `phase_done`, `scanclk` = `clk_74a`); `pll_dps.v` turns
  each request from `MEM_PHASE` into one step. The memory test sweeps the phase in 168 ps
  steps over a whole period, briefly reinitialises the SDRAM at each step, checks with hard
  patterns, logs the window and sets the middle of it. The bitstream starts at 9932 ps.
- **The sweep corrupts memory contents:** at bad phases the chip misreads commands and
  addresses. A checksum per MB before and after the sweep showed 15 of 63 MB changed, not
  only the 4 KB of the test. This is why the Pocket loads nothing into the SDRAM ahead of
  time (`deferload`) and the loader requests `program.bin` only after the sweep and the tests
  (`docs/soc.md`).
- **Constraints, exactly these** (`core_constraints.sdc`): `create_generated_clock -name
  dram_clk_pin -source [PLL output divclk] [get_ports dram_clk]` (without `-invert`; for
  the PLL with phase shift the source is `...|cyclonev_pll|counter[0].output_counter|divclk`);
  `set_output_delay -clock dram_clk_pin -max 2.3 -min -1.3` on all `dram_*` outputs and
  `dram_dq`; `set_input_delay -clock dram_clk_pin -max 6.6 -min 2.5` on `dram_dq`;
  `set_multicycle_path -setup -end 2` from `dram_clk_pin` to `clk_74a` and **no** hold
  multicycle (with `-hold 1` or `-setup 3` the read hold check becomes meaningless: a test
  project then showed 14 ns instead of the real 0.6 ns); `set_clock_uncertainty -add 0.3` for
  `clk_74a` <-> `dram_clk_pin`. `clk_74a`, the PLL output and `dram_clk_pin` must **never** be
  put in separate asynchronous groups (all SDRAM IO checks would silently disappear).
- **Build check:** after the timing analysis `tools/build.sh` has the four transitions
  `clk_74a` <-> `dram_clk_pin` (setup and hold, all corners) reported and aborts if one has
  0 paths, is under 0.5 ns, or the read hold is over 5 ns (a sign of a wrong multicycle).
- **IO registers:** `FAST_OUTPUT_REGISTER` on all SDRAM outputs, `FAST_OUTPUT_ENABLE_REGISTER`
  and `FAST_INPUT_REGISTER` on the data lines; `tools/check_budget.py` verifies in the fitter
  report that the registers sit in the IO cells.

**Read latency:** the SDRAM outputs a data word tAC after its edge r+CL-1 and holds it until tOH
after edge r+CL; the controller captures it with edge **READ + CL + 1 = READ + 3**
(parameter `READ_LATENCY` in the controller, named in the SDC comment at the multicycle:
the setup multiplicity is READ_LATENCY - CL + 1 = 2).

## SDRAM controller (`sdram.v`)

### Mode

- Mode register `0x221`: CL2, burst length 2, sequential, single-location writes (M9 = 1).
  Extended mode register (BA = 10): full array, drive strength `010` (25 %), as in Analogue's
  own controller (parameter).
- Addresses: byte address [25:0] -> bank = [12:11], row = [25:13], column = [10:1]. A
  **READ** always goes to the even column {[10:2], 0} and returns the whole 32-bit word: the
  halfword of edge READ+3 into [15:0], that of edge READ+4 into [31:16]; the CPU picks the
  bytes itself, address bits [1:0] and the mask are ignored for reads. A **WRITE** writes
  one halfword at column {[10:2], h} with DQM = ~mask[2h+1:2h]; halfwords without mask bits
  are skipped. A cache line (32 bytes = 16 columns) never crosses a row.
- **DQM:** 11 during initialisation, the inverted mask on WRITE, otherwise 00 (so on every READ
  and after it).
- **Open rows:** each bank keeps its last used row open; hit: immediate; other row: PRECHARGE,
  tRP, ACTIVATE, tRCD; bank closed: ACTIVATE, tRCD.
- **Spacing** (counted per bank, across job boundaries, at refresh and at row changes):
  PRECHARGE at the earliest at max(ACTIVATE + tRAS, last WRITE + tWR, last READ + 2); ACTIVATE
  at the earliest at max(PRECHARGE + tRP, ACTIVATE of the same bank + tRC, ACTIVATE of any bank +
  tRRD); after every READ no READ, WRITE, PRECHARGE or BURST TERMINATE for two clocks
  (otherwise the SDRAM cuts off the second halfword), in practice every READ occupies two
  clocks; **a WRITE at the earliest 6 clocks after the last READ** (`T_R2W`; at the chosen
  phase the SDRAM drives from about READ+1.74 T to READ+4.2 T plus tHZ).

### Sequence

- **Power-up:** all `dram_*` registers have fixed start values (NOP, CKE = 0, DQM = 11, data
  output off). Only once the SDRAM PLL is locked (synchronised and stable for 1024 clocks):
  CKE = 1, 16,384 clocks NOP (220 us > 200 us), PRECHARGE ALL, 2 x AUTO REFRESH, MRS, EMRS.
  **Not tied to `reset_n`:** the Pocket loads data slots while holding the core in reset; the
  SDRAM must run and be refreshed then too. If the PLL loses lock, the SDRAM counts as not
  ready, CKE goes to 0, and after re-locking the whole initialisation runs again.
- **Short reinitialisation** (`MEM_PHASE` bit 8, after each phase step): clock and CKE keep
  running; once the current job and its data are through, PRECHARGE ALL, 2 x AUTO REFRESH,
  MRS, EMRS. New jobs wait meanwhile instead of getting error words, and the contents are
  kept.
- **Refresh:** due every 512 clocks (6.9 us), executed between two jobs: PRECHARGE ALL (with
  the spacing above), AUTO REFRESH, tRFC. A job takes at most about 28 clocks, so the gap
  stays under 580. A 32-bit counter counts every AUTO REFRESH (`MEM_REFRESH`) so the firmware
  can check the rate on the Pocket.
- **Read:** one READ per 32-bit word; a cache line is 8 READs two clocks apart, the 16
  halfwords arrive without gaps. Each READ pushes a tag (port, epoch, last word) through a
  chain of length `READ_LATENCY`; the word is ready one clock after the first halfword and
  goes from a register to the port. The next job may begin while the previous one's data is
  still in flight (the spacing above still applies).
- **Write:** one WRITE per halfword with mask bits, data at the IO register.
- **Not ready:** while the SDRAM is not initialised, the controller answers read jobs at once
  with the right number of error words and discards write jobs. The CPU has no time limits;
  an unanswered job would halt it.
- **Pins:** separate `dq_o`/`dq_oe`/`dq_i`; the tristate is in `core_top`.

### Ports, arbiter and ordering (`sdram_port.v`)

A separate module between CPU, bridge and controller, so that the random test can drive it
directly (`soc.v` instantiates it unchanged):

- **One command register per CPU port** (iBus 1 entry, dBus 1 entry), loaded on acceptance
  with the already decoded target; `cmd_ready` = register empty, from registers only. Both
  ports can accept in the same clock.
- **Bridge write buffer** (4 entries): the Pocket delivers at most one word every 88 clocks;
  an overflow is held as an error bit.
- **Line port** for mixer (samples), rasterizer (textures), geometry unit (meshes) and
  blitter (images), shared among them in `soc.v` (mixer before rasterizer before geometry
  before blitter; the mixer rarely needs a line, but needs it by the next output value): one
  command register and up to **two lines in the controller**. The controller starts the next
  line while the words of the previous one are still arriving; closely following lines thus
  come at the spacing of the 8 READs instead of the full latency. Words return in job order;
  a two-entry FIFO in `soc.v` remembers whom they belong to. (At the start with all cars this
  cut the rasterizer's wait for textures from 299,000 to 188,000 clocks.)
- At every job boundary the arbiter picks: bridge buffer, then bridge read, then dBus
  register, then line port, then iBus register.
- **Ordering rule:** writes of one source run in the order of acceptance. Every read returns
  data that contains all writes accepted before it; an iBus read may also contain later ones.
  (A read after a write in the same port waits automatically, because the CPU continues only
  after acceptance and the arbiter does not let a register overtake.)
- **CPU reset:** CPU read jobs not yet begun are discarded; words of jobs already running in
  the controller are discarded by a 1-bit epoch in the tag (toggled on every CPU reset),
  however short the reset. Accepted CPU writes still run through, never after the reset.
  Arbiter and controller are not reset by `cpu_reset`, only the CPU registers.
- **"All writes done"** (`MEM_STATUS` bit 4): NOR over every stage that can hold an accepted
  write (dBus register, controller up to the last WRITE). No counter. An `lw MEM_STATUS` right
  after an `sw` reads 0 while the write is still in progress (into the SDRAM with a row
  change, 7 clocks after acceptance). It is needed when a unit reads data that the CPU has
  just written to the SDRAM, because writes to different targets can overtake each other.

### Address decoding

| Region | Condition | iBus | dBus |
|---|---|---|---|
| Boot RAM (32 KB) | [31:15] = 0 | yes | yes |
| SDRAM | [31:26] = `000100` (0x1000_0000) | lines | lines, writes |
| SDRAM uncached | [31:26] = `111101` (0xF400_0000) | bus error | single reads, writes |
| otherwise | | bus error | as in `docs/soc.md` |

"Bus error" on the iBus means `soc.v` answers itself with 8 words, error bit on words 0-6;
such lines never reach the arbiter.

### Bridge and data slots

Bridge addresses `0x1000_0000`-`0x13FF_FFFF` write into the SDRAM, byte order swapped as for
the boot RAM. Reading through the bridge works too (the Pocket saves the saved games this
way, `docs/soc.md`): the arbiter takes a bridge read word right after the write buffer, before
the dBus; the answer is ready as soon as the word is back, and the Pocket collects it only with
the next bridge word (`io_bridge_peripheral.v`: 88 clocks later at the earliest), so a running
line burst or a refresh in front of it fits.

Before each slot the Pocket asks with "Data slot request write" (0x0082); the acknowledge
comes once the SDRAM is ready, but after 2^21 clocks (28 ms) of waiting at the latest, so
that an SDRAM failure does not block start (bridge writes into the SDRAM are then discarded
and an error bit is set).

`MEM_BRIDGE_WORDS` counts the bridge words into the SDRAM; it and the overflow bit are cleared
at power-up and at the falling edge of `reset_n` (Reset Enter). Hence the firmware can tell
whether a slot was loaded in this run: on a firmware reload from the menu the Pocket writes
only the newly loaded slot.

## Registers

`SYS_FLAGS`, `MEM_STATUS`, `MEM_BRIDGE_WORDS`, `MEM_REFRESH` and `MEM_PHASE`
(`0xF000_0008`-`0xF000_0018`) are listed with their bits in `docs/soc.md`.

## Memory test (`firmware/memtest.c`)

The boot loader runs it at every start. One procedure per memory, described by (base,
uncached base, size, die size). Errors are logged with address, expected and actual value, and
read back twice uncached (three times the same wrong value points to writing or addressing,
varying values to read timing); at most eight error lines are logged per memory, after that
only counted. After each test one line with "ok" or "FAIL, errors n" and the clocks. Before
each test and every 64 KB inside it, test and address are in the log's header line, so a hang
shows its place. Each test sets a bit in `SYS_SIM` on success (bits 3..12, list in
`tools/sim_faults.sh`). The result goes into `debug.txt`, into `SYS_SIM` for the simulation,
and on the screen only on a failure (then the program does not start).

In this order:

1. **Ready:** wait up to 0.5 s for `MEM_STATUS` bit 1; log `SYS_FLAGS`, `MEM_STATUS` and
   `MEM_BRIDGE_WORDS`. If the SDRAM is not ready the SDRAM tests are skipped.
2. **program.bin:** the last SDRAM test in time: requested from the Pocket (header, then the
   file), header, size and CRC-32 checked, plus the "overflowed" and "dropped" bits.
3. **Phase window:** 80 steps of 168 ps (simulation: 4), at each one reinitialise briefly and
   check: 4 KB pseudo-random through cache lines (simulation: 512 bytes) and 64 bytes of
   alternating pattern uncached. The longest run of good steps (on the Pocket it wraps around
   the circle) goes into the log as a map (`#` good, `.` bad), start and length; the middle
   is set. Fewer than 8 good steps (simulation: 1) count as an error.
4. **Data bus:** walking one and zero on a word (uncached).
5. **Byte lanes:** for each partial store (sb at 0-3, sh at 0 and 2) write a fresh background
   word, exactly one store with a different value, read back uncached and compare with the
   background in which only the target bytes are new; then read a known word with lb, lbu, lh,
   lhu at every offset (sign checked).
6. **Address bus:** own values at `0` and every power of two, write all first, then read all
   back uncached.
7. **Patterns** over the first and the last window of 2 KB, D-cache flushed before every
   checking pass (`0x0000500F`), through cache lines: address as data and inverted,
   pseudo-random (xorshift, regenerated on checking), 0xFFFF0000 and 0xAAAA5555 (all 16 data
   lines toggle between the halfwords); then 2 KB in scrambled line order (row changes right
   after writing) and 256 random words, each written and read back uncached at once (the old
   word restored afterwards). Only the first and last window are tested so the data slots
   loaded into the SDRAM are left alone.
8. **Code from the SDRAM:** copy in `auipc a0, 0; ret`, call it, expect the address of the
   copy; then four times overwrite with `li a0, K`, `fence.i` and three NOPs, call, expect K
   (the old line is still in the I-cache each time). Each instruction is read back as a
   cache line beforehand, the way the I-cache fetches it; what the SDRAM corrupted never runs
   (a stuck data line would otherwise turn `auipc a0` into `auipc s0`).
9. **Refresh:** count `MEM_REFRESH` over 2 frames starting at a frame change, require at least
   128,000 per second (expected 74.25 MHz / 512 = 145,020).
10. **Write status:** open bank 0 row 0x800, one `sw` to row 0xC00 (PRECHARGE, ACTIVATE,
    2 x WRITE: 7 clocks), read `MEM_STATUS` at once (bit 4 = 0 expected), wait until 1, read the
    value back. The three accesses are in one function that sits exactly in one I-cache line:
    a line refill between `sw` and `lw` takes 16 clocks, longer than the write, and made the
    test fail depending on code layout.
11. **Measurement** (not a test): clocks for a cache line with an open row and with another
    row in the bank (the fastest of four measurements), MB/s read and write through the cache
    with an unrolled loop; the measured code is aligned to I-cache lines.

In the simulation (`SYS_FLAGS` bit 0) only the window size shrinks, never the sequence. The
log names the windows and the testbench checks them. The firmware fills the stack with a
pattern at start and logs the high-water mark.

Simulation result (all models, windows of 2 KB):

```
SDRAM slot: ok, cycles 474618
phase map ####
SDRAM write status: ok, cycles 13600
SDRAM line read: row hit 30 cycles, row miss 34; read 63 MB/s, write 95 MB/s
memtest: errors SDRAM 0
```

A cache line costs the CPU 30 clocks with an open row, 4 more (tRP + tRCD) on a row change in
the bank. The pattern loops are one loop per pattern without calls, the rare error case is
outside (`__builtin_expect`) so that VexRiscv's static branch prediction always hits: 5
instructions per word when checking. The whole test takes about 0.1 s on the Pocket (phase
sweep 10 ms, patterns 5 ms, refresh two frames), plus `program.bin`.

### Why the clock phase matters

The read data is captured on `clk_74a` from signals launched by `dram_clk`. The phase between
the two decides whether setup (too late) or hold (too early) is violated on the data lines,
and the usable window (a run of consecutive good steps) is narrower than a period. The sweep
measures it on the real board, where PLL jitter, board delay and the chip's tOH differ from
the timing model, and sets the middle of the window. The map in the log shows how wide the margin is.

## Verification

- **SDRAM model** (`sim/models/sdram_model.v`), written from the data sheet alone, with its own
  self-test (`sim/sdram_model`, one negative probe per rule): mode registers unknown until
  MRS and EMRS, command sequences, all timings in clocks, refresh interval, DQM latencies,
  truncated bursts, bus conflicts via the separate `dq_oe`; memory with a poison pattern. Clock
  convention: the model sees a command one edge after the controller (standing for the
  phase) and outputs halfword k from edge r+CL-1+k; the simulation then shows read latency
  CL+1 = 3. The real read edge is proven only by the timing analysis and the phase
  measurement.
- **Fault injection** (`tools/sim_faults.sh`): five runs of `sim/soc`, each with one fault
  built into the SDRAM model (DQM swapped, DQ8 stuck at 0, BA1 stuck at 0, row bit 12 follows
  bit 11, every 16,000th write beat missing). `SYS_SIM` must show exactly the predicted tests
  as failed, no more and no less (the reasoning per case is in the script), and the log must
  report a failure.
- **Random test** (`sim/sdram`): `sdram_port` + `sdram.v` + model, bus models exactly per the
  CPU's protocol. Addresses from a small pool (few rows per bank, row and bank boundaries, last
  row), pauses mostly 0-3 clocks, write followed by read of the same row, iBus and dBus in
  the same clock, write bursts, all seven masks, partial-word reads, CPU resets from 1 clock
  to longer than a job at random times, bridge words (88 clocks apart; a targeted fast burst
  must set the overflow bit), iBus lines outside the SDRAM. Checks: exact word count, first
  word at the earliest one clock after acceptance, no unrequested word, data equal to a shadow
  memory per the ordering rule, command order at the SDRAM equal to acceptance order, the
  "done" status bit never 1 with a write open, no model error; a watchdog reports a job
  without answer for 20,000 clocks. About every 20,000 clocks a short reinitialisation in the
  middle of traffic. Coverage counters per case; seeds 1-4 with 2 million clocks each pass
  (about 100 reinitialisations each, longest refresh gap 550 clocks).
- **Mutation check of the random test:** 14 deliberately built faults in `sdram.v` and
  `sdram_port.v`, each must make the random test fail, and each does: iBus before dBus in the
  arbiter (iBus reads old data), hold clock after READ removed (truncated bursts), epoch
  removed (word without request after a reset), status bit without the port register, refresh
  every 600 clocks, tRCD 1, tWR 1, READ->WRITE after 3 clocks (bus conflict), single read at
  the wrong column, only the lower halfword written, mask ignored, read latency 2, PRECHARGE
  to the wrong bank, refresh before tRP has elapsed.
- **System test** (`sim/soc`): the real firmware with all models; the bridge like the Pocket
  (88 clocks apart, waiting for the acknowledge before each slot); a reset in the middle of
  SDRAM traffic; the last run reports the slot test as skipped. All 13 bits in `SYS_SIM`
  (`0x80001FFF`), model without errors, longest refresh gap 533 clocks.
- **Timing analysis:** IO registers packed on all SDRAM pins, the four SDRAM transitions in
  all corners with positive slack (table above), phase in ps documented with VCO and counters.
- **Pocket:** memory test, phase window and result from `debug.txt`.
